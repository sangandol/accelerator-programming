# 第七部分　回顾与自测

第七部分讲推理服务之上的那一层：应用怎样使用模型。一次模型调用是什么、要花多少；怎样把调用接成带工具、检索和记忆的循环；许多个 agent 一起做事，时间和容量受什么限制；任务怎样才算可靠、怎样才算做完；最后读一个真实系统的源码。全部围绕一个贯穿的任务：自动估算一个模型能否放进一块卡、能容纳多长的上下文。正文用到第一、二部分（工作量与深度、Little 定律、同步）、第六部分（词元、KV cache、引擎、前缀缓存）和本部分前面的章，不需要 TPU 或 GPU 路线的内容。读完这一部分，就能为一个基于模型的应用写规格、估算它的时间和词元账、审查 AI 写出的编排代码。

## 这一部分的骨架

1. 一次调用是一个不记事的函数；时间约为 prefill 加上每个输出词元读一遍权重；输出词元比输入词元贵得多；窗口既是预算，又占服务器的 KV 显存。（定义 34.2、命题 34.4、定义 34.7、例 34.9）
2. 提示是规格，要写明输入、操作、交付物和验收；输出要分三步验收：完整解析、符合模式、内容与出处成立；格式正确不等于内容正确；能由程序精确算出的东西交给程序。（定义 34.10、定义 34.12、例 34.13、例 34.14）
3. 工具循环是"模型提出、程序检查并执行、结果写回"；参数完整才执行，错误要带类型，有限轮次只保证有限次尝试。（定义 35.1、命题 35.3）
4. 逐轮重发历史时，提交的输入量二次增长；前缀缓存省 prefill，稳定的内容放在前面；窗口预算照样要满足。（命题 35.4、例 35.6）
5. 检索与回答是两道条件；上下文、原始记录、任务状态、长期记忆和 KV cache 是五件事；摘要会丢信息。（命题 35.8、35.4 节、命题 35.11）
6. 多个 agent 的完成时间有 $\max(W/p,L)\le T\le W/p+(1-1/p)L$；任务吞吐受模型和工具两个共享服务约束；并发提高，总吞吐提高，每个工作者变慢。（命题 36.5、命题 36.8、例 36.9）
7. 可靠性靠原子领取加尝试编号和输入版本、任务检查点和事件记录、幂等与对账、带出处的结论、绑定实际操作的授权；会话结束、产物验收和目标达成是三件事。（命题 37.2、命题 37.7、定义 37.8、例 37.10、定义 37.11）
8. 读别人的系统，跟着一件事走；注释、当前代码和运行证据分开记；类型检查、写入成功和业务真实性分开问。（注 38.1、注 38.5、注 38.9）

**最常用的节。** 34.1、34.3、34.4、34.6、34.7 节；35.1、35.2、35.4 节；36.2、36.4 节；37.1、37.3、37.6 节。面试里"怎样让 AI 稳定地做一件事""多个 agent 一定更快吗""超时的写操作能不能重试"这类问题，答案都在这一部分。

**这时可以读的附录。** 附录 B 的 B.10 节（模型调用与编排的接口）；附录 C 的 C.10、C.11 节（给模型应用和多 agent 系统写规格、审查框架）；附录 F 的 F.1 节（最后几条是本部分的资料怎样读）。

## 自测题

**1.** 一次模型调用的时间由什么决定？为什么压缩输出比压缩输入更能缩短时间？

<details><summary>答案与出处</summary>

调用分 prefill 与 decode 两段：prefill 计算受限，每个新输入词元约 $2\Phi$ 次运算；decode 每个输出词元都要把权重读一遍，访存受限。在 B200 上跑一个 70B 的 bf16 模型，每个输入词元约 0.12 ms，每个输出词元约 17.5 ms，相差约 140 倍（命题 34.4、例 34.5）。前缀缓存只省 prefill，对输出无帮助。

</details>

**2.** 一个 128K 词元的上下文，在窗口里放得下，为什么服务器未必养得起？

<details><summary>答案与出处</summary>

窗口放得下只是请求合法（定义 34.7）。上下文里的每个词元还占着 KV cache：模型 M 每词元 320 KiB，128K 词元要 40 GiB；B200 + bf16 一行扣掉权重和预留只剩 40.4 GiB，只够一个这样的请求（例 34.1、例 34.9）。decode 的每一步还要读这些 KV。

</details>

**3.** 模型输出的 JSON 通过了模式检查，为什么还可能是错的？应当怎样验收？

<details><summary>答案与出处</summary>

模式只检查字段和类型。验收分三步：响应完整且能解析；符合模式；内容与出处成立（数字重算、单位检查、出处存在且支持断言）（定义 34.12、例 34.13）。能由程序精确算出的部分写进程序，让模型只做必须理解语言的抽取，并带着出处（例 34.14）。

</details>

**4.** 为什么 agent 循环的输入量随轮数二次增长？前缀缓存起什么作用，有什么限制？

<details><summary>答案与出处</summary>

服务不记得上一次调用，每一轮都要把全部历史重发：$n$ 轮的提交总量是 $nP+n(n-1)\Delta/2$，而不同的位置只有 $P+(n-1)\Delta$ 个（命题 35.4）。前缀缓存让重复的位置不必再 prefill，上下文越长收益越大（例 35.6）；但它按整页匹配，开头一变就全部落空（习题 35.7），不减少逻辑窗口，不省 decode。

</details>

**5.** 把一件事交给十个 agent，能快十倍吗？

<details><summary>答案与出处</summary>

不能。固定的任务图至少要 $\max(W/p,L)$，串行的依赖链不会因为加人手而缩短（命题 36.5）。实际还受模型和工具两个共享服务的容量限制（命题 36.8）；并发提高时每步用时变长，例 36.9 里 32 个工作者只快了约 16 倍。拆分还要多付词元：共享的材料放在开头才能共用缓存（例 36.7）。

</details>

**6.** 两个工作者怎样才不会领到同一个任务？一个很慢的旧工作者后来交上了结果，怎么办？

<details><summary>答案与出处</summary>

领取用"仅当状态仍是 `open` 才改成 `running`"的原子更新，并检查受影响的行数（例 37.1）。每次领取让尝试编号加 1；提交时同时检查状态、尝试编号和输入版本，过期的和重复的提交都进不来（命题 37.2）。工作者的产物先写到私有位置，接受后再发布。

</details>

**7.** 创建工单的请求超时了，能不能直接重发？

<details><summary>答案与出处</summary>

不能直接重发。客户端分不清"请求没有到达"和"已执行但返回丢了"，重发可能重复，不重发可能漏做（命题 37.7）。需要服务端的稳定去重标识、结果查询或对账；否则保留 `unknown`。任务检查点只记录本地状态，回滚不了外部效果。

</details>

**8.** 一个基于检索的系统答错了，怎样判断是检索的问题还是回答的问题？

<details><summary>答案与出处</summary>

总成功率是"检索到充分证据"的概率乘以"取得证据后答对"的概率，不会超过前者（命题 35.8）。分别统计两个环节：证据没检索到，换更大的回答模型也修不好；证据到了却答错，才是回答或验收的问题（例 35.9）。

</details>

**9.** 拿到别人的 agent 框架源码，先看什么？

<details><summary>答案与出处</summary>

跟着一件事走：谁提出下一步，谁允许它运行，结果写在哪里，什么条件让任务结束（38.1 节）。注释、当前代码和运行证据分开记（注 38.1）；"完成"最终在哪里变成状态，那里检查的是编号、写入成功还是业务真实性（注 38.5）；拦截器是否接在每一条入口上（注 38.9）。读源码的顺序见 38.7 节。

</details>

**10.** 任务 E（估算一个模型能否放进一块卡）要自动化，怎样做才让人信得过？

<details><summary>答案与出处</summary>

写成四项规格（例 34.11）；让模型只抽取配置字段并给出位置，算术全部由程序完成，验收程序重算每一格、检查单位和出处（例 34.14）；一百份配置并行做时，按依赖图和容量估算时间（例 36.9）；领取、提交、恢复、重试都按第 37 章处理；最后只有产物通过独立验收才计为成功，没检查过的配置明确列为未完成（例 37.9、定义 37.11）。

</details>
